# 31 - Shopify Customers API Landing MVP

## Summary

This milestone added the first Shopify Admin API landing path for customer data.

The goal was to write Shopify API-derived customer records into an isolated BigQuery `raw_load` table without replacing the existing CSV ingestion pipeline, modifying canonical `raw.shopify_*` tables, or changing downstream staging, marts, or business-facing analysis logic.

The milestone succeeded.

## What changed

Added a new Airflow DAG:

```text
dags/mm_shopify_api_customers_landing_mvp.py
```

This DAG:

- checks local output folder write access before starting an API job
- starts a Shopify Bulk Operation for customers
- polls until the Bulk Operation completes
- downloads the JSONL result locally
- parses customer records from JSONL
- loads customers into `raw_load.shopify_customers_api_latest`
- validates the API landing table
- writes a local landing summary

Added a validation query:

```text
sql/validation/shopify_api_customers_landing_validation.sql
```

This query validates:

- API customer landing row count
- duplicate Shopify customer GraphQL IDs
- duplicate Shopify legacy resource IDs
- missing legacy resource IDs
- missing customer emails
- row counts for CSV-derived raw, staging, and customer dimension tables
- API customer overlap with staging by legacy Shopify customer ID
- API customer overlap with staging and `dim_customers` by normalized email

The API landing local output structure now uses entity-specific subfolders:

```text
local_data/shopify_api_landing/products/
local_data/shopify_api_landing/customers/
```

## Review findings

The customers API landing table is structurally sound:

- no duplicate API customer GraphQL IDs
- no duplicate Shopify legacy customer IDs
- no missing legacy customer IDs
- strong overlap with the existing CSV-derived staging customers table by Shopify customer ID

The main review item is:

```text
api_customers_missing_email = 816
```

This is not automatically a failure. Customers without email may be legitimate, but the project currently uses `customer_email` as the practical customer key for business-facing customer analysis. These records should remain visible in future customer reconciliation work.

The legacy ID overlap is very strong:

```text
21388 / 21389 staging customers matched by Shopify customer ID
```

This suggests that Shopify legacy customer ID will be a strong reconciliation key for future customer API-vs-CSV comparison.

## Design decisions

This milestone is landing-only.

It intentionally does not:

- replace Shopify CSV ingestion
- modify canonical `raw.shopify_customers`
- modify `staging.stg_shopify_customers`
- modify `marts.dim_customers`
- modify customer analysis models
- schedule API ingestion
- use API customer data as the warehouse source of truth

The existing CSV ingestion path remains the known-good fallback.

Current migration path:

```text
Shopify API -> isolated API landing tables -> API-vs-CSV comparison layer -> eventual canonical raw rebuild
```
